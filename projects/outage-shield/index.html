Outage Shield

Making vendor outage signals actionable in ServiceNow. A scoped Personal Developer Instance application that maps third-party status information to internal Service Offerings, applies preliminary business-risk rules and supports governed ITSM response.

Platform: ServiceNow PDI Integrations: GitHub and Cloudflare status APIs Scope: Designed, built and validated independently
Controlled automation: Outage Shield includes a configurable safety switch that separates live vendor monitoring from automated ITSM actions. Incident creation, priority escalation and Major Incident proposals were successfully validated through controlled testing.

01 / The challenge

Outage alerts need business context.

GitHub and Cloudflare publish technical status information about their services. That information does not, by itself, tell an organisation which internal services might be affected or whether an investigative Incident should be created.

Outage Shield connects vendor-reported components to ServiceNow Service Offerings, applies a preliminary risk assessment and guides a proportionate response while preserving human control over Major Incident declaration.

Why I built it

Having spent over 20 years running technology-led businesses, I've seen how technical problems quickly become operational problems. What interested me about ServiceNow was the opportunity to connect technology, business processes and practical decision-making.

With Outage Shield, I wanted to go beyond simply retrieving API data and creating Incidents. The interesting challenge was determining which services might actually be affected, when an Incident was justified and how to automate the response without losing human oversight.

02 / Solution design

From vendor API to service-aware response

A structured process converts external incident data into internal service context and an auditable action.

  1. Poll vendor status APIs

    Scheduled requests retrieve GitHub and Cloudflare data and process the returned JSON.

  2. Correlate components to Service Offerings

    Mapping records identify potentially affected internal offerings instead of treating all vendor components equally.

  3. Assess preliminary business risk

    Vendor severity is considered alongside Service Offering criticality, with uncertain or invalid evidence routed to review.

  4. Apply native ITSM governance

    Controlled tests validate investigative Incident creation, escalation on an existing record and a proposal—not automatic declaration—of a Major Incident.

  5. Prepare subscriber communications

    When possible offering impact starts or clears, events generate queued notifications for eligible subscribers; unchanged conditions suppress duplicate event batches.

Design decisions and trade-offs

I wanted Outage Shield to use ServiceNow's existing capabilities wherever practical, rather than build custom functionality unnecessarily.

  • Use the standard priority matrix. I used ServiceNow's Impact/Urgency matrix to calculate Incident priority instead of assigning priority numbers directly in custom code.
  • Reuse Incidents rather than create duplicates. Repeated vendor updates should not generate a new Incident every five minutes. I designed the application around one primary Incident per vendor outage.
  • Keep Major Incident declaration under human control. A severe vendor outage can justify a Major Incident proposal, but it doesn't prove the organisation is experiencing a Major Incident. Declaration remains a human decision.
  • Handle uncertainty rather than assume impact. Missing service mappings, conflicting vendor information and invalid API responses require safeguards. I chose to flag uncertain situations for review instead of automatically escalating them.

03 / Decision policy

Proportionate escalation, with human oversight

Preliminary risk drives the response. Incident priority is calculated using ServiceNow's configured Impact/Urgency matrix rather than directly equating risk labels to priority numbers.

Low

Monitor

Continue observing status signals; no automatic investigative Incident.

Medium

Investigate · P3 target

Create a standard investigative Incident for potential impact.

High

Escalate · P2 target

Create or increase priority on the existing primary Incident.

Very high

Propose Major Incident

Create an investigative Incident and submit a native proposal for human assessment. Never auto-declare.

05 / What was validated

Clear evidence boundaries

Demonstrated in Version 1

  • Live REST polling and processing of GitHub and Cloudflare status data.
  • Vendor component-to-Service Offering mapping and risk context.
  • Controlled Incident creation, primary-Incident reuse and P3 → P2 escalation.
  • Native Major Incident candidate proposal for human review.
  • Four fail-safe test paths passed.
  • Subscriber event generation and queued outbound email records.

Not claimed as validated

  • Production deployment or live business-user acceptance.
  • External email receipt or delivery beyond the PDI outbox.
  • Unattended native ITSM writes enabled during the live polling test.
  • HTTP timeout, retry and upstream transport-failure recovery.
  • Automatic declaration of a Major Incident.
